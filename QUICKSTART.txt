THE ORDER: 1886 FOR PC - QUICK START (LINUX)

WHAT THIS DOWNLOAD INCLUDES

Unofficial, emulator-backed compatibility software, not an official PC port.
Two files carry it:

- The-Order-1886-x86_64.AppImage: the launcher and the dedicated
  compatibility runtime with its libraries, in one file. The launcher is
  Tkinter and the image carries its own Python, so nothing has to be
  installed to open its window.
- order1886-linux-x86_64-*.tar.gz: the plain package, the same runtime with
  "Play The Order 1886" for direct play.

No game executable, game archives, firmware or player saves are included.
Use your own extracted PS4 copy of The Order: 1886, in any edition:
CUSA00076 (tested), CUSA00035, CUSA00070, CUSA00100, CUSA00670 or CUSA00785
(experimental: report how they run). Update 1.02 may be applied or not.

REQUIREMENTS

- x86-64 Linux with glibc 2.39 or newer (SteamOS 3.6+, Ubuntu 24.04+, Debian
  13, Fedora 40+, Arch) and a Vulkan driver for your GPU.
- Nothing to install for the settings window: no WebKitGTK, no GTK and no
  Python of your own. The launcher is Tkinter running on the image's Python.
- AppImage: make it executable once, chmod +x The-Order-1886-x86_64.AppImage
  (Desktop Mode: right-click > Properties > Permissions > Executable).
- Plain package: extract the complete archive to a writable folder and keep
  both entry points and bin together.

YOUR GAME FOLDER

Choose the folder that directly contains eboot.bin, archivemap.bin, _data,
sce_sys and sce_module (any folder name). The original files are only read.

STARTING THE LAUNCHER (APPIMAGE)

Start the AppImage. The window opens on Home; on Game & Content choose your
game folder, then press Play. Every page and setting comes from the runtime's
own catalogue (Display, Graphics, Performance, Controls, Game & Content,
Achievements, System), and each change is saved as you make it. Settings keep
their defaults (30 FPS) until you change them.

WITHOUT THE WINDOW (STEAM, GAME MODE, A SECOND SHORTCUT)

  ./The-Order-1886-x86_64.AppImage --direct-play

starts the game with the saved settings. Add --game-dir the first time and the
folder is checked and saved, so later starts need only --direct-play:

  ./The-Order-1886-x86_64.AppImage --direct-play --game-dir "/path/to/CUSA00035"

In Steam (Desktop Mode): Games > Add a Non-Steam Game, browse to the AppImage,
then put --direct-play in the entry's launch options. Start it from Steam in
Game Mode or Desktop Mode. --help lists the options. The plain package does
the same with "Play The Order 1886", which takes --game-dir too.

WHERE SETTINGS LIVE

Settings, prepared images, logs, caches and saves are kept in user/order1886
beside the launcher: next to the AppImage, or in ~/.local/share/order1886 when
that folder cannot be written. ORDER1886_STATE chooses the folder yourself, a
good place for it being Steam's launch options. While playing, F10 cycles the
frame rate live: 60, 90, 120, back to 30 (rates above 60 need a display that
refreshes that fast, or VSync off).

FSR 4 (THIS INSTALLATION)

This copy was rebuilt with AMD FSR 4 support: Graphics -> Upscaling ->
AMD FSR 4 replaces the game's own temporal anti-aliasing at the game's render
size (keep Render resolution on Original 1920). FSR 3.1 is selectable on
Linux here too and is the automatic fallback. The bin/fsr4 folder must stay
beside the runtime; without it the game's own anti-aliasing stays and the
session log says why. Details: docs/verification/2026-11-08-fsr4-linux.md.

CONTROLLERS (XBOX, PLAYSTATION AND OTHER GAMEPADS)

Connect the pad before you launch, then start the game. When the runtime opens a
pad it writes "Runtime: gamepad connected: <name>" to the boot log in
user/order1886/logs and buttons work immediately. To check detection without
starting the game: bin/order1886-runtime --gamepad prints one line, either
"Gamepad: type=xbox360 ... name=..." or "Gamepad: none".

The launcher's runtime entry also prints "Order1886: pad check:" warnings when a
pad cannot work. Each has a concrete fix:

- "the running kernel has no module folder" or "visible on USB but no driver
  took it": your distribution cannot load the Xbox kernel drivers (xpad,
  hid-microsoft). This is not a game problem. The usual cause is a kernel update
  without a reboot: /lib/modules/$(uname -r) is gone, so no driver loads.
  Reboot into the installed kernel. Verify the pad reaches the kernel first:
  grep -A4 -i xbox /proc/bus/input/devices must show an event/js device;
  ls /dev/input/by-id | grep -i 045e must list the pad.
- "is present but your user cannot read it": the session grants no HID access,
  common with Bluetooth pads. Grant access once: sudo usermod -aG input $USER
  (log out and in), or install this udev rule and replug:
  echo 'KERNEL=="hidraw*", SUBSYSTEM=="hidraw", MODE="0660", GROUP="input"' \
    | sudo tee /etc/udev/rules.d/61-order1886-pad.rules
  sudo udevadm control --reload && sudo udevadm trigger
- Everything looks right but buttons do nothing in-game while the pad works
  elsewhere: Steam is grabbing the pad exclusively. Quit Steam while playing,
  or disable Steam Input for that controller family in Settings > Controllers.

Xbox pads: wired pads use xpad; Xbox Series/Elite Bluetooth pads use
hid-microsoft or xpadneo. If the pad sleeps, press the Xbox button to re-open
it. The runtime cannot use a pad that the kernel has not exposed.

MOUSE AND KEYBOARD

For the closest thing to a PC shooter with mouse and keyboard, open the game's
Options > Controls and set LOOK, AIM and SCOPE SENSITIVITY to 8 of 10. The
mouse drives the PS4 right stick, so the game's own sensitivity sets how fast
the camera can turn; at the default, medium and fast mouse motion hit that
limit and need a lot of mousepad.

Esc releases the mouse (to leave the window); press F6 in the game window to
capture it again. No restart is needed.

Fine-tuning: write user/order1886/mouse-tuning.ini (window_ms, deadzone, curve,
gain; see docs/order1886-input.md in the engine repository). The running game
re-reads it about twice a second. Delete it to return to the defaults.

SHADER CACHE AND SEEDS

The game records every pipeline it compiles under
user/order1886/gpu/native-ps4-v1/cache/<TITLE_ID>/ and replays that record
while the game boots, so areas you have already visited do not stutter again.
Since v0.2.24 this folder really is inside the package: earlier Linux copies
fell back to ~/.local/share/shadPS4. Since v0.2.28 that old folder is no
longer copied in (it only holds caches from other builds); it is left
untouched and you may delete it. If a boot ever crashes while
replaying the cache, the next launch renames the cache to
<TITLE_ID>.crashed-<run> and rebuilds it, so just launch again.

A friend can hand you their recorded cache as a "seed bundle": put the
folder they gave you at  <package>/shader-cache/CUSAxxxxx/  and launch.
Every file is checked against the bundle's manifest first; a bundle that
does not match your GPU/driver is ignored and the cache rebuilds by playing,
exactly as without it; a cache that already has real sessions is never
overwritten. To make a bundle of your own:

  python3 scripts/order1886_cache.py --export \
    user/order1886/gpu/native-ps4-v1/cache/CUSA00035 \
    --out <someone-elses-package>/shader-cache/CUSA00035 \
    --title CUSA00035

Play at least once with "Background pipeline warmup" on to fill the cache.
A seed replays only when the other machine's GPU feature profile matches the
capture exactly; on any difference (different card, driver or runtime build)
the runtime discards it and rebuilds by playing, so sharing helps closest
setups and is harmless elsewhere.

UPDATING

Replace the AppImage with the new one: the user folder beside it stays, and
it holds settings, saves and logs. For the plain package, extract the new
archive and copy your "user" folder from the old one into it.
